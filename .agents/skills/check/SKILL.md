# check — 다관점 검증

**읽기 전용: 코드 수정과 커밋을 하지 않는다.**

## 입력

$ARGUMENTS

> Claude Code 는 위 자리에 슬래시 명령 인자를 넣는다. 비어 있거나 `$ARGUMENTS` 가 그대로 보이면 사용자 메시지에서 대상을 읽는다.

- 커밋이나 범위가 있으면 그 커밋부터 현재까지(`<커밋>..HEAD` 와 미커밋 변경)를 본다.
- 없으면 `git status`, `git diff HEAD` 의 현재 변경분을 본다.
- 프로젝트 전체를 훑지 말고 변경된 파일과 영향받는 사용자 흐름을 기준으로 본다.

## 단계

1. **1차 검증 (관점별 병렬)**
   - 사용자별 오답노트 데이터 격리, 인증과 인가 누락 (`permission-auditor`)
   - N+1, JPA 풀스캔, 페이지네이션과 인덱스, 커넥션풀 (`perf-reviewer`)
   - null/empty, 동시성, 예외와 롤백, 비즈니스 정합성 (`logic-reviewer`)
   - FCM 실발송 경로, 잘못된 MySQL 쓰기, 데이터 오염 (`db-safety`)
   - 마이그레이션 파일이 있으면 Flyway 안전성 (`migration-safety`)
   - DTO 나 엔드포인트가 바뀌면 Flutter 앱 호환성 (`api-contract-checker`)

   Claude Code 에서는 괄호 안의 `.claude/agents/` 서브에이전트를 동시에 투입한다. 서브에이전트가 없는 환경(Codex 등)에서는 같은 관점을 직접 순서대로 확인한다.

2. **2차 반증**
   - 발견한 문제가 실제로 도달 가능한지, 상위 validation 이나 권한 체크, 트랜잭션 경계가 이미 막는지 확인한다.
   - 한 관점이 찾은 문제를 다른 관점이 놓쳤는지, 판단이 서로 충돌하는지 다시 본다.
3. **실행 검증**: 가능하면 관련 테스트, `./gradlew compileJava` 같은 정적 검사를 제안하거나 실행한다. 못 했으면 이유를 적는다.
4. **자가 반증 질문**에 답하고 필요하면 위험도를 고친다.
   - 내가 놓쳤을 가능성이 큰 것은?
   - 이 변경이 실제 사용자에게 깨질 수 있는 경로는?

## 산출물

위험도 순서로 보고한다. 각 항목에 `파일:라인`, 사용자 영향, 수정 방향을 적는다. 추정은 근거로 쓰지 않는다.

- 🔴 즉시 수정 필요 (사용자 영향, 데이터 오염, 보안)
- 🟠 배포 전 수정 권장 (성능 저하, 예외 미처리)
- 🟡 다음 이터레이션
- 🟢 이상 없음

마지막에 실행하지 못한 검증과 자가 반증 결과를 짧게 적는다.
