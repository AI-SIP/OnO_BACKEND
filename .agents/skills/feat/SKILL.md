# feat — 기능 구현

## 작업

$ARGUMENTS

> Claude Code 는 위 자리에 슬래시 명령 인자를 넣는다. 비어 있거나 `$ARGUMENTS` 가 그대로 보이면 사용자 메시지에서 작업을 읽는다.

## 단계

1. **기준 확인**: 계획서(`docs/plans/`)나 작업 설명을 읽는다. 인자가 없으면 `git status`, `git diff HEAD` 의 현재 변경분을 읽고 남은 구현을 파악한다.
2. **계획과 승인**: 기준이 없거나 불명확하면 영향 범위를 조사해(Claude Code 에서는 `code-tracer` 에이전트) 간략한 계획을 제시하고 **승인을 기다린다**. 승인 전에는 구현하지 않는다.
3. **구현**: 승인된 범위 안에서만 바꾼다. 임의 확장, 과한 추상화, 무관한 리팩터링을 하지 않는다.
   - 계획서와 실제 코드가 다르면 실제 코드를 기준으로 판단하고 차이를 설명한다.
   - 모든 데이터 접근에 `userId` 소유권 검증을 빠뜨리지 않는다.
   - API 계약과 DTO, validation, 예외 처리, 트랜잭션, 로그를 확인한다.
   - DB 스키마 변경은 Flyway 마이그레이션(`migrate`)으로 한다. `ddl-auto` 를 `create` / `create-drop` 으로 바꾸지 않는다.
   - FCM 발송 경로나 운영 DB 에 영향 가는 변경은 먼저 경고하고 확인받는다.
4. **컴파일 확인**: `./gradlew compileJava` 를 실행하고 오류가 있으면 고친다.
5. **커밋하지 않는다**: 변경은 작업 트리에 남긴다. 테스트 작성과 실행은 `test`, 실제 커밋은 `commit` 에서 한다.
6. **자가 반증 질문**에 답하고 필요하면 추가 수정하거나 리스크로 보고한다.
   - 내가 놓쳤을 가능성이 큰 것은?
   - 이 변경이 실제 사용자에게 깨질 수 있는 경로는?

## 완료 보고

- 변경한 파일과 내용
- 사용자 영향
- 실행한 검증과 결과
- 남은 리스크나 확인 질문
- 논리 단위별 커밋 분할 제안

> 다음 순서: `test` → `check` → `commit` → `pr`
